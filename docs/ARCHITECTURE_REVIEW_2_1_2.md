# Architecture Review — baseline 2.1.2

Дата аудита: 23 июля 2026

## Итог

Текущая версия пригодна как стабильная база для дальнейшей разработки. В проекте уже есть понятное разделение на страницы, данные, API, layout, общие стили и заготовки дизайн-системы. Главный технический долг сейчас не в отсутствии компонентов, а в том, что созданные Foundation-компоненты пока не подключены ни к одной странице, а большая часть визуальной логики остаётся внутри scoped-стилей отдельных страниц.

Рекомендуемая стратегия: не проводить массовую миграцию. Сначала безопасно проверить типографические компоненты на одной простой странице, затем переносить только те элементы, чьи размеры и селекторы полностью контролируются.

## Что уже сделано хорошо

- Единый `AppLayout` управляет метаданными, навигацией, диалогами и уведомлениями.
- Глобальные переменные вынесены в `variables.css`.
- Общие стили подключаются централизованно через `global.css`.
- API, работа с базой, авторизация и UI-утилиты разделены по каталогам.
- Есть документация по архитектуре, дизайну, книге, дневнику и roadmap.
- Для анимаций предусмотрен `prefers-reduced-motion`.
- Приватные и редакторские маршруты получают `noindex` автоматически.
- Foundation-примитивы уже созданы и имеют небольшой, понятный API.

## Ключевые находки

### 1. Foundation существует, но фактически не используется

Компоненты `Heading`, `Text`, `Eyebrow`, `Quote`, `Container`, `Section`, `Stack`, `Cluster`, `Paper`, `Card` и `Divider` не импортируются ни одной текущей страницей.

Это означает, что дизайн-система пока является подготовленной библиотекой, а не реальной основой интерфейса. До её постепенного внедрения нельзя считать миграцию завершённой.

**Приоритет:** высокий.

### 2. Scoped CSS тесно связан с нативной HTML-разметкой

На страницах много селекторов, рассчитанных на конкретные вложенные `h1`, `h2`, `p`, `small` и другие элементы. Оборачивание содержимого в дочерний Astro-компонент меняет область scoped-стилей и уже приводило к визуальной регрессии.

**Следствие:** механическая замена `<h1>` на `<Heading>` по всему проекту небезопасна, даже когда компонент рендерит тот же HTML-тег.

**Правило миграции:** сначала одна страница, затем визуальная проверка, только после этого расширение области изменений.

### 3. Две страницы слишком велики

- `src/pages/lines/[id].astro` — около 917 строк.
- `src/pages/pages/[id].astro` — около 912 строк.

В них одновременно находятся загрузка данных, разметка, интерактивность и большой объём CSS. Это усложняет поиск ошибок и делает любые архитектурные изменения рискованными.

**Рекомендация:** не разбивать их в рамках Typography Migration. Позже отдельно вынести навигацию чтения, панель действий, диалог удаления и клиентскую логику. Каждый вынос должен быть отдельной задачей с визуальным сравнением.

### 4. Типографика пока управляется на трёх уровнях

Одновременно действуют:

1. базовые правила `h1–h4` и `p` в `global.css`;
2. классы Foundation в `foundation.css`;
3. scoped-стили конкретных страниц.

Это допустимо на переходном этапе, но создаёт риск каскадных конфликтов. Например, `Heading` всегда добавляет `.ds-heading`, который задаёт цвет, размер, line-height и `text-wrap`; существующая страница может ожидать другие значения.

**Рекомендация:** на первом этапе использовать Foundation-компоненты в «нейтральном режиме» либо передавать существующий класс и убедиться, что базовые правила компонента не меняют computed styles.

### 5. Не каждый текст должен стать компонентом `Text`

Служебные сообщения, счётчики символов, статусы черновика, подписи кнопок, ошибки формы и `small` внутри карточек имеют собственную семантику и поведение. Массовая замена всех `<p>` на `<Text>` увеличит связность и не даст реальной пользы.

**Рекомендация:** мигрировать только повторяющиеся редакционные тексты и заголовки. Служебный UI пока оставить нативным.

### 6. Есть повторяющиеся паттерны, но их нельзя объединять преждевременно

Повторяются:

- eyebrow + title + lead;
- диалоги подтверждения удаления;
- счётчик символов и статус черновика;
- пустые состояния;
- переходы «предыдущая / следующая»;
- листы оглавления и дневника.

Часть из них действительно станет компонентами, но сначала нужно стабилизировать типографику и поверхности. Иначе один большой универсальный компонент быстро получит слишком много вариантов.

### 7. CSS организован логично, но часть истории релизов осталась внутри файлов

В `global.css` присутствуют комментарии и блоки предыдущих релизов. Это не ошибка, но со временем файл будет сложнее читать.

**Рекомендация:** позднее объединить связанные глобальные правила и оставить историю изменений только в `CHANGELOG.md`. Сейчас это не приоритет.

### 8. Inline styles используются только для CSS-переменных анимации

Найдено три случая `style=`. Все они передают индекс или задержку через CSS custom properties. Это обоснованное применение и не требует исправления.

## Карта риска

| Область | Риск | Решение |
|---|---:|---|
| Замена всех заголовков сразу | Высокий | Пилот на одной странице |
| Замена всех абзацев | Высокий | Мигрировать только редакционный текст |
| `Container` / `Section` на всех страницах | Высокий | Отложить до отдельной задачи |
| `Heading` на простой странице | Низкий–средний | Сравнить computed styles |
| Документация и naming | Низкий | Можно менять независимо |
| Surface-компоненты | Средний | После Typography Migration |
| Разбиение reading-страниц | Высокий | Отдельные небольшие задачи |

## Рекомендуемый порядок работ

### TASK-003A — Typography Pilot

Страница: `404.astro`.

Почему она подходит:

- небольшая;
- нет данных из базы;
- нет сложного клиентского скрипта;
- легко сравнить визуально;
- содержит eyebrow, `h1`, основной текст и footer-текст.

Задача считается завершённой только после проверки desktop и mobile.

### TASK-003B — Static Typography

После успешного пилота:

- `login.astro`;
- `unspoken.astro`;
- `lines/index.astro`;
- `book.astro`.

Не включать редакторы и reading-страницы в этот этап.

### TASK-003C — Editor Typography

Отдельно мигрировать заголовки и подсказки редакторов. Не трогать статусы, сообщения ошибок и счётчики.

### TASK-003D — Reading Typography Review

Для `lines/[id].astro` и `pages/[id].astro` сначала составить таблицу computed styles и только потом решать, даёт ли компонентизация реальную пользу. Вполне допустимо оставить нативную типографику внутри Reading Experience, если она намеренно уникальна.

### TASK-004 — Surface Migration

Начать с одного пустого состояния или одной простой карточки. Не создавать универсальную «карточку всего».

### TASK-005 — Layout Cleanup

`Container`, `Stack` и `Section` внедрять только после стабилизации scoped CSS-контрактов.

## Definition of Done для v2.1.3

- На пилотной странице отсутствуют визуальные отличия.
- Семантические HTML-теги не ухудшены.
- Scoped CSS продолжает применяться.
- Нет массовой замены служебных `<p>`.
- Build проходит локально у владельца проекта.
- В VS Code нет новых Problems.
- После каждого шага можно выполнить простой rollback одного коммита.

## Решение по текущему baseline

Архив принят как рабочая база `2.1.2`. Он не требует срочного переписывания. Следующее безопасное изменение — не полная Typography Migration, а `TASK-003A: Typography Pilot` на странице 404.

Такой подход займёт на один шаг больше, но практически исключает повторение регрессии со scoped CSS.
